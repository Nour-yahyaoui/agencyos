# Security audit — 2026-11-07

Scope: source review of the Next.js web app, NestJS API, serverless adapter and npm dependency graph. This is a targeted audit, not a penetration test or a guarantee of security. No production data was modified and no production login was attempted. The live deployment is separate from this PR.

## Ten-step review

1. **Inventory and trust boundaries.** Reviewed the web app, API, serverless adapter, deployment configuration and shared-source synchronization. The web proxy and API are separate deployment targets; changes must be deployed to both where applicable.
2. **Authentication and session lifecycle.** Refresh rotation had a race that could create two successors. Rotation now claims the old session and creates its successor transactionally; reuse revokes the family. Disabled accounts cannot receive a new session. Reset tokens are claimed atomically and other outstanding reset tokens are invalidated. Remaining: access tokens remain valid until expiry after logout or password reset; a reset/refresh race and revocation of already-issued access tokens need a dedicated session-version design and database concurrency tests.
3. **Tenant and role authorization.** The organization guard trusted an organization header even on a conflicting organization path, allowing access to another organization's detail endpoint. It now rejects conflicts. Manually triggered reminders now operate on the requester's organization. The project and client activity feeds are limited to internal roles.
4. **Object-level and client isolation.** Invoice list filters previously overwrote client and draft restrictions, allowing a client to request other clients' invoices or drafts. They now intersect with the mandatory scope. Invoice update now checks tenant and client/project consistency. Client details no longer disclose draft invoices or internal notes; requested client IDs are intersected with scope. Invoice and project detail responses no longer include full client records. Document lists for developers are restricted to assigned projects or unassociated files. More broadly, response fields and cross-tenant relationships require ongoing review.
5. **CSRF and origin checks.** Public auth mutations now reject a foreign browser Origin even before a session exists; cookie-authenticated mutations still require the double-submit token. CSRF comparison now checks byte lengths safely, rejecting malformed tokens rather than throwing. Origin-less non-browser requests remain allowed by design.
6. **Recovery and privacy.** Production password recovery now returns the same response for known and unknown users without exposing the email delivery result. The web UI no longer assumes that a missing delivery flag means email was not configured. Development-only reset links remain intentionally available outside production.
7. **Uploads and request handling.** The serverless adapter previously buffered entire request bodies before limits were applied. It now bounds JSON/other bodies and multipart requests, and returns 413 or 400 for oversized or malformed bodies. Document downloads use Express's attachment encoding and `nosniff`; local storage paths enforce directory boundaries. MIME types are still client-supplied: consider content inspection, malware scanning, isolated storage and retention controls. Hosting platforms may impose smaller request limits than the application.
8. **Browser, email and integrations.** Notification email text is HTML-escaped. Swagger no longer persists bearer credentials in browser storage. Stripe signature and amount checks were reviewed in code, but no real payment flow was exercised. Swagger still loads assets from a third-party CDN; pin and integrity-protect or self-host them. Review the AI provider's data processing and prompt-injection controls before sending sensitive data.
9. **Dependency and configuration review.** `npm audit --omit=dev` initially reported eight affected packages (seven high, one moderate). Root npm overrides replace vulnerable nested Multer and PostCSS versions in the checked-in workspace lockfile. The subsequent audit reports four affected packages, all high: `zod`, `prisma`, `@prisma/config`, and `deepmerge-ts` (the latter three form the Prisma dependency chain). npm recommends major upgrades; assess compatibility and upgrade with integration tests. The overrides must also be honored by the deployment install process; verify deployed dependency trees. Prisma CLI's deepmerge issue concerns recursive configuration objects; exposure depends on how configuration is supplied. Do not interpret package counts as independent vulnerabilities or assume exploitability without further analysis.
10. **Verification and operational follow-up.** Added unit and integration regression cases. Lint, API build/typecheck and unit tests are run locally with a generated Prisma client in no-engine mode; this does not exercise real database operations. Database-backed integration tests, concurrent refresh/reset tests, browser tests, uploads, webhook flows and production verification require suitable isolated infrastructure. Deploy only after reviewing these gaps, then validate both production deployments and monitor.

## Urgent operational checks

- A previous production web configuration had demo mode enabled, and the seed script contains publicly known demo credentials, including a platform-admin account. This audit did **not** verify whether those accounts exist or can log in to production. Immediately verify the production database and disable/remove demo accounts, especially any super-admin, or rotate credentials and isolate demo data. Hiding the login buttons alone does not disable accounts.
- Rotate any real secrets that were exposed, review audit logs for unauthorized access, and use an incident-response process if compromise is suspected. Do not put secrets in Git or tickets.
- Serverless throttling uses in-memory per-instance counters; use a shared rate-limit store or edge protection for effective distributed abuse prevention.
- Review bcrypt's 72-byte password truncation and migrate to a compatible password-hashing scheme with a safe transition for existing users.
- The serverless local-storage fallback is ephemeral; configure durable private storage before relying on uploads. Verify role restrictions, backups, retention and malware handling.
